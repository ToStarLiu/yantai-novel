# 小说创作工作台：首版设计与开发边界

初版日期：2026-11-12；更新：2026-11-13。状态：本文件保留首版实施基线，后续完整系统、跨端、协作和Pi作者流程由D-016至D-022及阶段07/08扩充；首版暂缓项不代表当前缺失清单。作者质量评估后置，当前工程进度见[阶段总纲](../plans/2026-11-12-novel/README.md)。

已确认：用户选择 **Web 自托管版**，并授权按本计划开始实施。本文架构作为实施基线；修改时同步更新受影响的阶段计划，已完成状态以验收证据为准。

## 1. 产品目标

服务正在创作中文长篇小说的个人作者。作者能管理作品、编辑章节、让 AI 按章纲起草和检查，在确认正文与记忆变更后继续写作；修改旧稿时，系统能说明哪些后续内容需要复核。

首版成功标准是作者完成作品时的修改时间和事实错误减少。AI 自评分、Agent 数量、生成总字数均不能单独证明成功。

原始研究文档是候选能力与参考资料；本设计确定首版范围。实现细节与原研究冲突时，以本设计和明确记录的后续决策为准。

## 2. 产品形态与路线比较

| 路线 | 优点 | 代价 | 本次决定 |
|---|---|---|---|
| Web 自托管，Go + React + PostgreSQL | 统一数据库和任务模型，浏览器使用，适合验证长篇流程 | 用户需要运行服务，部署与备份必须有说明 | 已由用户选择 |
| 桌面单机，嵌入式数据库 | 安装后使用，本地文件体验自然 | 桌面打包、升级与服务版数据兼容增加工作量 | 首版不实施 |
| 文件与命令行为中心的验证工具 | 验证成本低，结果容易检查 | 缺少持续创作体验 | 仅用于阶段 00 的验证入口 |

首版是单作者实例：不做团队、多租户计费、公开注册和协作。允许保存多部作品，作品之间的数据和检索必须隔离。

“自托管”指数据、后端和数据库由用户控制；调用云模型仍会向选定服务发送组装后的上下文，界面需要展示这一行为。

## 3. 全局约束

以下条目由各阶段计划原样引用，适用于所有实现任务。

- 首版为单作者 Web 自托管；Go 后端、React/TypeScript 前端、PostgreSQL 唯一业务数据库。
- 正文 Revision 不可变；任何 AI 修改生成候选版本，作者决定是否采用。
- 正文和作者确认的设定是权威来源；摘要、状态快照和检索索引必须保留来源并能重建。
- 长期记忆只从已确认正文或作者明确设定形成；AI 提议经过校验和作者确认后才能生效。
- 模型调用与任务记录绑定；浏览器断开不等于取消任务，明确取消才改变任务状态。
- 状态提交校验输入正文版本和基线状态版本；过期结果保留供查看但不得覆盖当前状态。
- 阶段验收使用固定样例和可检查证据；未执行的检查不得记录为通过。

## 4. 首版范围

必须交付：

1. 作品、人物、世界设定、卷和章节管理；TXT/Markdown 导入与导出。
2. 章纲、正文编辑、自动保存、历史版本与逐项接受/拒绝 AI 修订。
3. 单章起草、一致性审稿、定向修订；流式查看输出。
4. 人物位置、物品、伤势、人物知识和少量伏笔的叙事状态。
5. 有来源证据的记忆变更审核，正文定稿与状态提交分开显示。
6. 旧稿变更导致的记忆失效、后文影响报告和受控重建。
7. 带作品、版本、叙事位置约束的历史检索和引用展示。
8. 可查看与恢复的任务、费用记录、项目导出和恢复。

首版暂缓：可视化工作流编辑器、通用工具型 Agent、自动整书无人值守、知识图谱数据库、多人协作、桌面壳、移动端、平台发布、封面/音视频、本地 GPU 推理运维和模型训练。

## 5. 技术基线

| 部分 | 首版决定 | 演进条件 |
|---|---|---|
| 后端 | Go，标准库 HTTP + chi，模块化单体 | 模块有独立扩容需求时才拆服务 |
| 数据 | PostgreSQL，pgx + sqlc，SQL 迁移 | 首版不兼容 SQLite |
| 前端 | React + TypeScript + Tiptap，TanStack Query | React Flow 与协作编辑按实际需求评估 |
| 模型 | 统一 Provider 接口，先接一个兼容接口；另有确定性假 Provider | 第二个 Provider 用契约测试接入 |
| 推送 | SSE 事件流；数据库中的事件可重新读取 | 首版不引入 SignalR |
| 任务 | PostgreSQL Job + 租约 + 尝试记录；API/Worker 使用同一代码库 | 长流程恢复复杂度超过现有模型时单独决策 Temporal |
| 检索 | 先结构化查询和关键词；阶段 04 评估 pgvector 的增益 | 评估证明有价值才把向量链路设为默认 |
| 部署 | Docker Compose，前端由服务同源提供；TLS 可由反向代理终止 | 部署性能有证据后再改变拓扑 |

Go 版本下限沿用原方案的 1.24；阶段 00 开始时核对官方支持状态并锁定实际受支持的工具链。Node、包管理器和依赖同样在初始化时记录确切版本并提交锁文件。文档不把某个日期的“最新版”写成长期保证。

不单独搭建 Python 服务：使用外部模型/Embedding 服务不要求项目维护 Python 推理部署。Temporal、Qdrant、MinIO 也不是首版启动依赖。

## 6. 核心数据与职责

| 对象 | 职责与关键字段 |
|---|---|
| Project | 作品隔离边界；当前可用状态版本、规划版本、状态健康标记 |
| Chapter / ChapterBlueprint | 稳定章节 ID、展示顺序、章纲、当前编辑版本和已定稿版本 |
| ChapterRevision | 不可变正文、父版本、作者/AI 来源、关联 Run、内容哈希 |
| ReviewIssue | 关联具体正文版本；证据锚点、原因、严重度、作者处理状态 |
| GenerationJob / JobAttempt | 业务意图、输入快照、状态、尝试、租约、取消请求、调用结果 |
| RunArtifact / RunEvent | 已保存的章纲、草稿、报告、原始响应和可续读事件 |
| NarrativeStateVersion | 父状态、来源正文版本、投影 Schema、结构化快照、健康状态 |
| MemoryChangeSet | 基线状态、来源正文版本、提议变更、证据、审核结果 |
| StoryFact / CharacterBelief | 客观事实与角色信念分开；来源、有效时间、揭示位置、确认状态 |
| Dependency / ImpactReport | 来源变化影响了哪些状态、报告、草稿和检索记录 |
| RetrievalChunk | 可重建索引；作品、正文版本、实体、叙事位置和故事时间 |

数据库 ID 由服务端生成。模型可以引用输入中的已有 ID；新增实体使用临时引用，校验后由服务端分配稳定 ID。

ReviewIssue 的定位使用 `revisionId + plainTextHash + quote + prefix + suffix`。服务端基于该版本定位引用，无法唯一定位时显示“需定位”，不直接采用模型给出的字符偏移。

富文本 JSON 是正文编辑的权威表示，保存对应纯文本及内容哈希用于模型输入和证据引用；Markdown 是导入导出格式。AI 文本先保存为独立候选，不直接拼接进正在编辑的文档。

## 7. 叙事状态与两种时间

状态至少覆盖五类：人物位置、伤势、物品归属、角色已知/推测/误信的信息、伏笔状态。

- 叙事位置：`chapterId + chapterOrder + sceneOrder`，表达文本读到哪里。
- 故事时间：`day + label + precision`，day 可为空，表达事件发生在何时。
- 事实的有效时间、向读者揭示的位置、角色获取信息的位置分别保存。
- 未知时间、含糊关系和无证据的推测允许保留未知；不得补造精确日期或事实。

首版支持记录倒叙/插叙，但只对已知可比较时间执行确定性时间校验。复杂平行时间线和自动世界模拟不属于首版；无法判定时输出需人工判断的问题。

作者计划中的未来事件、未采用草稿与已经发生的事实分别存放，不进入同一事实池。

## 8. 正常写作与状态提交

```text
作者确认章纲
→ 创建持久任务并冻结输入正文/状态/Prompt/模型配置
→ 生成候选草稿并保存输出
→ 对选定正文版本审稿
→ 作者选择问题并申请修订
→ 比较候选与当前稿，作者采用/手改
→ 作者定稿
→ 提取 MemoryChangeSet
→ 规则校验与证据检查
→ 作者确认记忆变更
→ 事务内提交新状态版本和派生更新事件
→ 后台更新索引
```

章节“正文已定稿”与“记忆已确认”是两个可见状态。记忆未就绪时，后续生成可以准备章纲，但不能静默使用过期状态起草；用户看到具体阻塞原因。

网络调用不放在数据库事务内。任务完成后提交时检查输入版本是否仍匹配；不匹配则标为过期候选，保留输出和费用记录。

## 9. 旧稿修改、失效与重建

1. 编辑已定稿章节只创建新 Revision；旧版本仍可查看。
2. 新版本被确认为定稿时，计算依赖影响：直接事实、之后的状态快照、依赖这些状态的草稿/审稿和索引。
3. 首版采取保守策略：从变化章节起的后续状态全部标记待重建；对正文给出复核建议，不自动改后文。
4. 作者选择重建，系统从修改点之前最后一个有效状态开始，逐章提取和审核变更。
5. 作者锁定的设定或人工纠正也记录来源；重建遇到冲突时列出问题，不静默覆盖。
6. 旧快照与索引可保留历史，但活动检索必须过滤失效正文版本。

重排、删除章节同样产生影响报告。首版每部作品只维护一条活动正文线；历史候选不构成可并行续写的故事分支。

## 10. 任务与外部调用语义

基础持久任务从首次真实模型调用开始引入；阶段 05 补齐故障窗口、租约竞争、恢复控制和容量治理。

最小状态：`Pending / Running / WaitingForUser / Succeeded / Failed / Cancelled / NeedsReconciliation`。阶段 05 扩展 `Paused / RetryScheduled`；业务状态和每次网络调用状态分别记录。

“请求重试”和“作者要求再生成一次”是不同意图：前者复用意图 ID，后者创建新意图 ID。唯一约束避免一个意图重复创建业务任务。

提供商已执行但本地未收到结果时记录 `NeedsReconciliation`。仅在提供商明确支持且经验证时使用其幂等键或结果查询；否则提示结果未知，避免自动重试昂贵调用。不承诺所有提供商绝不重复计费。

关闭页面只断开 SSE 订阅；取消按钮提交持久取消请求。只在当前可中断操作上执行取消。已经产生的输出和费用保留。

## 11. 作者入口、配置与数据保护

单实例仅一个作者身份：部署时配置作者凭据，使用后端会话登录；无公开注册。访问控制覆盖项目 API、任务、SSE、导出和静态以外的数据入口。默认开发绑定回环地址；远程部署文档包含 TLS 与持久卷配置。

首版模型密钥从后端环境/挂载秘密文件读取，界面仅显示脱敏配置与密钥引用，日志不输出密钥。Prompt、原始响应和正文日志按作品导出/清理，默认不写入常规应用日志。

项目导出包含正文版本、设定、章纲、已确认事实、状态来源和必要配置快照，不包含模型密钥和登录凭据。数据库备份负责完整实例恢复；项目包负责单作品迁移，两者分开验收。

## 12. 阶段与依赖

```text
00 技术与质量基线
→ 01 作者工作台
→ 02 有证据的叙事记忆
→ 03 旧稿影响与状态重建
```

阶段 00 必须先证明单章链路与评估方法可用；后续功能按阶段退出标准验收。早期先建立正确的任务、版本与来源边界，不提前实现复杂编排。

## 13. 验证策略

离线确定性测试负责版本冲突、状态规则、作品隔离、索引可见性和任务副作用。真实模型实验负责语言质量、信息提取效果与作者修改成本；测试中不得假装 LLM 输出可逐字稳定复现。

评估使用同一模型、同一章纲、同一输出上限的三种配置：A 最近正文与人工设定；B A 加结构化状态；C B 加历史检索。记录上下文大小与实际成本，避免把更多 Token 的收益全部归功于架构。

先用 3 章固定样例排查工程错误，再用 10 章故事验证正常推进和至少两次旧稿修改，发布前用 20 章样例和真实作者试用。硬事实和角色知识有人工标注的标准答案；主观文风由作者评价。

首版质量门槛、计算口径和实际结果登记在阶段06与评估协议中。阶段00实现、测试和三轮真实模型结果见[基线记录](../../../evaluation/baseline-status.md)；后续完整系统和Pi作者流程以各自测试与[系统验收](../../release/acceptance.md)为据，不能把基线、连通测试或UI完成当成文学质量与作者修改时间达标。
